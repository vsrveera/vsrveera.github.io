34  Mixture-of-Experts, Scale and Numerical Precision

NoteKey ideas
  • A mixture-of-experts (MoE) layer has many MLPs but sends each token through only \(k\) of them. Total parameters grow, active parameters (and FLOPs) do not.
  • A router (softmax over experts) picks the experts. A load-balancing loss keeps all experts used.
  • Training a dense model costs about \(C\approx6ND\) FLOPs for \(N\) parameters and \(D\) tokens.
  • Test loss falls as a power law in model size and data, with diminishing returns.
  • Numerical precision is a design variable: the formats float32, float16, and bfloat16 trade range against resolution.

34.1 The system problem

A larger model is a better model, up to a point. But every parameter in a dense model is used for every token, so compute grows with size. And large models are trained in 16-bit arithmetic, which has its own failure modes.

How can parameters grow without compute growing as fast, and what limits training at scale?

34.2 Mixture of experts

In a dense Transformer block, one MLP processes every token. An MoE layer replaces it with \(E\) expert MLPs and a small router. For each token \(\mathbf{x}\):

  1. The router computes probabilities \(\mathbf{p}=\text{softmax}(\mathbf{W}_{r}\mathbf{x})\in\mathbb{R}^E\) (Chapter 24).
  2. The top-\(k\) experts are chosen. Their weights are renormalised: \(g_i=p_i/\sum_{j\in\text{top-}k}p_j\).
  3. The output is the weighted sum of the chosen experts:

\[ \mathbf{y}=\sum_{i\in\text{top-}k(\mathbf{x})}g_i(\mathbf{x})\,\text{Expert}_i(\mathbf{x}). \tag{34.1}\]

Each token touches \(k\) of the \(E\) experts. The model has \(E\) times the MLP parameters of a dense block, but each token pays for only \(k\) of them.

import torch, torch.nn as nn, torch.nn.functional as F

class MoE(nn.Module):
    def __init__(self, d, n_experts=4, k=1, hidden=32):
        super().__init__()
        self.E, self.k = n_experts, k
        self.router = nn.Linear(d, n_experts, bias=False)
        self.experts = nn.ModuleList([nn.Sequential(nn.Linear(d, hidden), nn.GELU(),
                                                    nn.Linear(hidden, d)) for _ in range(n_experts)])

    def forward(self, x):                                    # x: (tokens, d)
        p = F.softmax(self.router(x), dim=-1)                # (tokens, E)
        topv, topi = p.topk(self.k, dim=-1)
        g = topv / topv.sum(-1, keepdim=True)                # renormalised gate weights
        out = torch.zeros_like(x)
        for e in range(self.E):
            sel = (topi == e)                                # (tokens, k) bool
            rows = sel.any(-1)
            if rows.any():
                w = (g * sel).sum(-1)[rows].unsqueeze(-1)
                out[rows] += w * self.experts[e](x[rows])    # only routed tokens are computed
        f = F.one_hot(topi[:, 0], self.E).float().mean(0)   # fraction of tokens whose top choice is e
        aux = self.E * (f * p.mean(0)).sum()                 # load-balancing loss
        return out, aux, f

m = MoE(d=8, n_experts=8, k=2)
x = torch.randn(1000, 8)
y, aux, f = m(x)
print("output shape:", tuple(y.shape))

      f"(×{moe_params / dense_params:.1f});  active per token: {m.k} experts + router")

34.2.1 Active versus total parameters

For a realistic block, the accounting is simple. We compare dense and MoE versions of a Mixtral-style configuration.

def moe_model_params(V, d, L, h, n_kv, f, E=1, k=1):
    dh = d // h
    attn = 2 * d * d + 2 * d * n_kv * dh
    expert = 3 * d * f                                       # SwiGLU
    router = d * E if E > 1 else 0
    total = V * d + L * (attn + E * expert + router + 2 * d) + d
    active = V * d + L * (attn + k * expert + router + 2 * d) + d
    return total, active

dense = moe_model_params(32000, 4096, 32, 32, 8, 14336)
moe = moe_model_params(32000, 4096, 32, 32, 8, 14336, E=8, k=2)
print(f"dense : total {dense[0] / 1e9:5.1f} B   active {dense[1] / 1e9:5.1f} B")
print(f"MoE   : total {moe[0] / 1e9:5.1f} B   active {moe[1] / 1e9:5.1f} B   (8 experts, top-2)")
print(f"MoE has {moe[0] / dense[0]:.1f}x the parameters for {moe[1] / dense[1]:.1f}x the per-token compute")
dense : total   7.1 B   active   7.1 B
MoE   : total  46.6 B   active  12.7 B   (8 experts, top-2)
MoE has 6.5x the parameters for 1.8x the per-token compute

The memory to hold the model follows the total. The compute per token follows the active parameters. MoE trades memory for compute.

34.2.2 Load balancing

If a router prefers one expert, that expert gets most tokens and the others learn little. In a distributed system with experts on different devices, it also leaves devices idle. A standard remedy is an auxiliary loss. Let \(f_i\) be the fraction of tokens whose top choice is expert \(i\), and \(P_i\) the mean router probability for expert \(i\):

\[ \mathcal{L}_{\text{aux}}=E\sum_{i=1}^{E}f_i\,P_i. \tag{34.2}\]

When routing is uniform (\(f_i=P_i=1/E\)), \(\mathcal{L}_{\text{aux}}=1\). When all tokens go to one expert (\(f=P=\text{one-hot}\)), it is \(E\). By Cauchy–Schwarz, for \(f=P\) the sum \(\sum f_i^2\) is smallest at the uniform distribution, so the loss pushes towards balance. It is added to the training loss with a small coefficient.

E = 8
uniform = np.full(E, 1 / E)
print("uniform routing        : aux =", round(E * np.sum(uniform * uniform), 3))
one_hot = np.eye(E)[0]
print("all tokens to expert 0 : aux =", round(E * np.sum(one_hot * one_hot), 3))
rng = np.random.default_rng(0)
vals = [E * np.sum(q * q) for q in rng.dirichlet(np.ones(E), size=1000)]
print("random routing (f = P) : min over 1000 draws =", round(min(vals), 3), "(never below 1)")
uniform routing        : aux = 1.0
all tokens to expert 0 : aux = 8.0
random routing (f = P) : min over 1000 draws = 1.098 (never below 1)

34.2.3 An experiment: does the balance loss work?

We build a task with four clusters of tokens, each with its own linear target map, and train an MoE with four experts and top-1 routing, with and without the balance loss.

def run_moe(aux_coef, seed):
    torch.manual_seed(seed); d = 8
    cent = torch.randn(4, d) * 3; maps = torch.randn(4, d, d) / math.sqrt(d)
    moe = MoE(d, n_experts=4, k=1, hidden=32)
    opt = torch.optim.Adam(moe.parameters(), lr=3e-3)
    def data(n):
        c = torch.randint(0, 4, (n,)); x = cent[c] + torch.randn(n, d)
        return x, torch.einsum("bij,bj->bi", maps[c], x)
    for _ in range(600):
        x, y = data(256)
        out, aux, _ = moe(x)
        loss = F.mse_loss(out, y) + aux_coef * aux
        opt.zero_grad(); loss.backward(); opt.step()
    with torch.no_grad():
        x, y = data(4000); out, _, f = moe(x)
    return F.mse_loss(out, y).item(), f.numpy()

Without the balance loss, some experts are used far less than others (in both seeds, one expert receives about 2% of the tokens). Even a small coefficient (\(0.01\)) makes the load almost uniform, and a tenfold larger one changes little. In this small task, forcing uniform routing also made the model less accurate (MSE about 0.12–0.18 against 0.04–0.06): the router can no longer assign each token freely to its best expert. Real systems accept this cost because balanced load is needed for hardware efficiency, and they use a small coefficient.

34.3 The cost of training: \(C\approx6ND\)

For a dense model with \(N\) parameters trained on \(D\) tokens, the compute is about \(6ND\) floating-point operations.

TipDerivation

Consider one linear layer with weight matrix of \(N_\ell\) entries, applied to \(B\) tokens. A matrix product of \((B,n_{\text{in}})\) with \((n_{\text{in}},n_{\text{out}})\) costs \(2Bn_{\text{in}}n_{\text{out}}=2BN_\ell\) FLOPs (Chapter 5).

  • Forward: \(2BN_\ell\).
  • Backward (Chapter 18): the input gradient \(\mathbf{G}\mathbf{W}^{\intercal}\) costs \(2BN_\ell\), and the weight gradient \(\mathbf{X}^{\intercal}\mathbf{G}\) costs another \(2BN_\ell\). Total \(4BN_\ell\).

Per token and per parameter: \(2+4=6\) FLOPs. Summing over all weights and all \(D\) tokens gives \(C\approx6ND\). (Attention score computation adds a smaller \(T\)-dependent term.) \(\blacksquare\)

def train_flops(N, D):
    return 6 * N * D

print(f"{'model':>10s} {'tokens':>10s} {'FLOPs':>10s} {'A100-class GPU-days at 40% util.':>34s}")

    days = C / (0.4 * peak) / 86400
    print(f"{N:10.1e} {D:10.1e} {C:10.1e} {days:34,.0f}")

Training a 7B-parameter model on a trillion tokens needs about \(4\times10^{22}\) FLOPs, which is thousands of GPU-days. Inference costs about \(2N\) FLOPs per token, a third of one training token’s forward and backward.

34.3.1 Where the FLOPs go: context length

Per token, the dense layers cost about \(2\cdot12d^2=24d^2\) FLOPs per block. Attention over a context of length \(T\) adds \(4Td\) (scores and weighted values). They are equal at \(T\approx6d\).

34.4 Scaling laws

Empirically, the test loss of language models falls as a power law in parameters, data, and compute, when the other factors are not the bottleneck:

\[ L(N)\approx\Bigl(\frac{N_c}{N}\Bigr)^{\alpha}+L_\infty. \tag{34.3}\]

On a log–log plot, loss minus the floor is a straight line with slope \(-\alpha\). Published large-scale studies find exponents of the order \(0.05\)–\(0.1\): a tenfold increase in size reduces the reducible loss by only a modest factor. Such laws let one predict, from small runs, how a larger run will behave.

We run a miniature version with the character model of Chapter 33, at six widths. Every run has 2 blocks and 1,000 steps at the same learning rate. This is a demonstration of the method, not a measurement of a law.

from pydoc_data import topics
raw = " ".join(topics.topics[k] for k in sorted(topics.topics)).lower()
keep = set("abcdefghijklmnopqrstuvwxyz .,\n")
text = " ".join("".join(c if c in keep else " " for c in raw).split())[:300_000]
chars = sorted(set(text)); Vc = len(chars); ixc = {c: i for i, c in enumerate(chars)}
data = torch.tensor([ixc[c] for c in text]); ntr = int(0.9 * len(data))
tr, va = data[:ntr], data[ntr:]
Tc = 64

class SBlock(nn.Module):
    def __init__(self, d, H=4):
        super().__init__()
        self.H = H
        self.l1, self.l2 = nn.LayerNorm(d), nn.LayerNorm(d)
        self.qkv, self.o = nn.Linear(d, 3 * d), nn.Linear(d, d)
        self.m = nn.Sequential(nn.Linear(d, 4 * d), nn.GELU(), nn.Linear(4 * d, d))
    def forward(self, x):
        B, T, d = x.shape
        q, k, v = self.qkv(self.l1(x)).chunk(3, -1)
        sp = lambda t: t.view(B, T, self.H, d // self.H).transpose(1, 2)
        a = F.scaled_dot_product_attention(sp(q), sp(k), sp(v), is_causal=True)
        x = x + self.o(a.transpose(1, 2).reshape(B, T, d))
        return x + self.m(self.l2(x))

class SLM(nn.Module):
    def __init__(self, d, L=2):
        super().__init__()
        self.E, self.P = nn.Embedding(Vc, d), nn.Embedding(Tc, d)
        nn.init.normal_(self.E.weight, std=0.02); nn.init.normal_(self.P.weight, std=0.02)
        self.b = nn.ModuleList([SBlock(d) for _ in range(L)]); self.ln = nn.LayerNorm(d)
    def forward(self, i):
        x = self.E(i) + self.P(torch.arange(i.shape[1]))
        for b in self.b:
            x = b(x)
        return self.ln(x) @ self.E.weight.T

def batch(src, B=64):
    st = torch.randint(0, len(src) - Tc - 1, (B,))
    return torch.stack([src[s:s + Tc + 1] for s in st])

widths = [16, 32, 48, 64, 96, 128]

        opt.zero_grad(); loss.backward(); opt.step()

        torch.manual_seed(1); b = batch(va, 512)
        losses.append(F.cross_entropy(lm(b[:, :-1]).reshape(-1, Vc), b[:, 1:].reshape(-1)).item())
    print(f"width {d:4d}: {Ns[-1]:8,d} parameters, validation loss {losses[-1]:.3f}")

Two lessons. Bigger is better with diminishing returns. And scaling laws need the other resources (data, steps, learning rate) to grow with the model. Compute-optimal scaling studies tune all of them together.

34.5 Numerical precision

A floating-point number has a sign, an exponent (range), and a mantissa (resolution). The three common training formats split 16 or 32 bits differently.

print(f"{'format':10s} {'bits':>5s} {'exp':>4s} {'mant':>5s} {'machine eps':>12s} {'max':>10s} {'min normal':>12s}")
for name, dt, e, m in [("float32", torch.float32, 8, 23), ("float16", torch.float16, 5, 10),
                       ("bfloat16", torch.bfloat16, 8, 7)]:
    fi = torch.finfo(dt)
    print(f"{name:10s} {fi.bits:5d} {e:4d} {m:5d} {fi.eps:12.2e} {fi.max:10.2e} {fi.tiny:12.2e}")
format      bits  exp  mant  machine eps        max   min normal
float32       32    8    23     1.19e-07   3.40e+38     1.18e-38
float16       16    5    10     9.77e-04   6.55e+04     6.10e-05
bfloat16      16    8     7     7.81e-03   3.39e+38     1.18e-38
  • float16 has more mantissa bits than bfloat16 (finer resolution) but a small range: it overflows above 65,504 and underflows below \(6\times10^{-5}\) (normal) or \(6\times10^{-8}\) (subnormal).
  • bfloat16 has the same range as float32 but coarse resolution (about 2–3 decimal digits). It rarely overflows. It rounds aggressively.

34.5.1 Accumulation error

Adding many small numbers to a large running sum loses them. Once the sum is large, each small term is below half the spacing between representable numbers and is rounded away.

total16 = np.float16(0.0); total32 = np.float32(0.0)
for _ in range(100_000):
    total16 = np.float16(total16 + np.float16(1e-4))
    total32 = np.float32(total32 + np.float32(1e-4))
print(f"sum of 100,000 × 1e-4 (true value 10.0):  float16 {float(total16):.4f},  float32 {float(total32):.4f}")
sum of 100,000 × 1e-4 (true value 10.0):  float16 0.2500,  float32 10.0063

The float16 sum stalls near 0.25, where \(10^{-4}\) is smaller than half the spacing of float16 numbers. This is why matrix-multiply hardware accumulates in float32 even when inputs are 16-bit, and why softmax, normalisation, and loss sums are done in float32.

34.5.2 Gradient underflow and loss scaling

Gradients can be tiny. In float16, values below about \(6\times10^{-8}\) become exactly zero. Loss scaling multiplies the loss by a large factor (e.g. \(2^{16}\)) before the backward pass, which scales all gradients by the same factor, and divides afterwards in float32.

g_true = np.array([1e-9, 1e-8, 1e-7, 1e-6, 1e-4], dtype=np.float64)
plain = g_true.astype(np.float16)
S = 2.0 ** 16
scaled = (g_true * S).astype(np.float16).astype(np.float32) / S
print("true gradients     :", g_true)
print("float16            :", plain.astype(np.float64))
print("with loss scaling  :", scaled.astype(np.float64))
print("exp(12) in float16 :", np.exp(np.float16(12.0)), " (overflow: max is 65504)")
true gradients     : [1.e-09 1.e-08 1.e-07 1.e-06 1.e-04]
float16            : [0.00000000e+00 0.00000000e+00 1.19209290e-07 1.01327896e-06

with loss scaling  : [1.00044417e-09 9.99716576e-09 1.00000761e-07 1.00024045e-06

exp(12) in float16 : inf  (overflow: max is 65504)

bfloat16 does not need loss scaling, because its range equals float32’s. That is a main reason it became the default for large-model training.

34.5.3 Mixed precision in practice

A standard recipe keeps a float32 master copy of the weights and optimiser state, runs the forward and backward passes in bfloat16, and accumulates in float32. Memory per parameter with Adam: 2 bytes (bf16 weight) + 4 (fp32 master) + 4 + 4 (Adam moments) + 2 (gradient) = 16 bytes.

for N in (7e9, 70e9):
    bytes_per_param = 2 + 4 + 4 + 4 + 2
    print(f"{N / 1e9:4.0f} B parameters: weights+optimiser state ≈ {N * bytes_per_param / 2**30:,.0f} GiB "
          f"(excluding activations)")

  70 B parameters: weights+optimiser state ≈ 1,043 GiB (excluding activations)

34.6 Production

PyTorch’s autocast runs selected operations in lower precision while keeping others (softmax, normalisation, reductions) in float32. We check the effect on one layer.

torch.manual_seed(0)
lin = nn.Linear(512, 512)
x = torch.randn(64, 512)
ref = lin(x)
with torch.autocast("cpu", dtype=torch.bfloat16):
    y = lin(x)
rel = ((y.float() - ref).norm() / ref.norm()).item()
print(f"output dtype under autocast: {y.dtype};  relative error vs float32: {rel:.1e}")
print("bf16 resolution near 1.0:", torch.tensor(1.0, dtype=torch.bfloat16).item(),
      "→ 1 + 2^-8 rounds to", float(torch.tensor(1.0 + 2 ** -8, dtype=torch.bfloat16)))
output dtype under autocast: torch.bfloat16;  relative error vs float32: 2.9e-03
bf16 resolution near 1.0: 1.0 → 1 + 2^-8 rounds to 1.0

34.7 Failure modes

Expert collapse. The router sends most tokens to a few experts. The others never train. Remedies: a balance loss, noise in the router, expert capacity limits.

Router instability. Router logits can grow large, making routing erratic and softmax saturate. A small penalty on the log-sum-exp of the router logits (a “z-loss”) keeps them bounded.

Token dropping. With a fixed expert capacity, tokens routed to a full expert may be dropped. This changes the output between training and inference.

Loss spikes. Large runs show sudden loss increases, often linked to rare large gradients, overflow in attention logits, or optimiser state in low precision. Gradient clipping and careful normalisation reduce them.

Overflow and underflow. Float16 needs loss scaling and float32 for softmax. Check for inf and nan.

Non-determinism. Summing in a different order gives different rounding. Two runs on the same data may differ in the last digits, then diverge.

Extrapolating scaling laws. A power law fitted on a narrow range may fail outside it. Laws depend on how data, learning rate, and architecture are scaled together.

Chapter summary

  • MoE: \(\mathbf{y}=\sum_{i\in\text{top-}k}g_{i}\text{Expert}_i(\mathbf{x})\). Total parameters scale with \(E\), active parameters with \(k\).
  • The balance loss \(E\sum_if_iP_i\) is 1 at uniform routing and larger otherwise.
  • Training costs \(\approx6ND\) FLOPs. Inference costs \(\approx2N\) per token.
  • Attention FLOPs equal the dense FLOPs at \(T\approx6d\).
  • Loss follows a power law in size with diminishing returns, if data and training scale with it.
  • float16 has resolution and little range. bfloat16 has range and little resolution. Accumulate in float32.
